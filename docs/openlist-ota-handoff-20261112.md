# OpenList 管理 AI：ArtemisOS OTA 下载链路调查交接

> 后续决策已确定：使用 `/d/` → 天翼云直连，更新器支持安全 HTTPS 跳转，不做旧客户端代理迁移。当前实现与验证见 [直连 OTA](openlist-direct-ota.md)。以下保留为调查时点的历史事实，不再是待执行方案。

## 目标与边界

请评估最佳部署实践，优先让 Windows 客户端从网盘/CDN 直接下载补丁，避免更新文件长期经 OpenList 服务器中转。不默认开启全局「强制代理分享文件链接」，也不影响其他分享。

需要同时解决：现有 1.0.2、1.0.4 等旧用户如何迁移，以及新更新器如何使用直链。先调查并给出推荐方案；本说明不表示任何候选方案已经验证。

## 已验证事实

- 产品：Windows 原生 Android 模拟器 ArtemisOS 15。
- OTA 服务入口：`https://cloudx.playones.com/sd/YCsIY2UB/?d`。这是旧客户端已保存的地址，不能假设先改所有用户的配置。
- 文件布局：`manifests/<当前版本>.json`、对应 `.sig`、`objects/<SHA256>`。对象按哈希寻址；客户端先验清单签名，再检查下载大小、对象哈希和被替换文件的旧哈希。
- 清单根据当前版本给出下一跳，当前最新版本返回签名的「无更新」清单。1.0.2→1.0.3→1.0.4→1.0.5→1.0.6→1.0.7，需要每一跳正常完成启动后再检查下一跳。
- 2026-11-12 10:57（UTC+8）使用真实旧下载函数重新检查以下路径：

| 原地址下的路径 | HTTP | Content-Type | 跳转目标主机 |
|---|---|---|---|
| `manifests/1.0.2.json?d` | 302 | text/html; charset=utf-8 | media-qhxn-fj-person.qh6oss.ctyunxs.cn |
| `manifests/1.0.2.sig?d` | 302 | text/html; charset=utf-8 | 同上 |
| `objects/f28488ce4343e44be980a463d6e47fb3ee308e550d41fbfaf0856d24da91757c?d` | 302 | text/html; charset=utf-8 | 同上 |

- 没有跟随上述请求的跳转；没有在交接文件中保存带签名的临时下载 URL。
- 之前用允许跳转的独立读请求能够得到正确的清单和有效签名。文件没有因此丢失；浏览器下载成功不能证明旧更新器可用。
- 旧客户端 `update/core.ps1` 的 `Open-UpdateResponse` 明确设置 `AllowAutoRedirect = $false`，User-Agent 是 `ArtemisOS-Updater/1`。读取元数据未显式拒绝 302，导致跳转 HTML 被当成清单或签名；已见签名 Base64 解析错误。
- 发布端 `tools/Publish-OpenList.ps1` 也禁止跳转，匿名回读要求成功响应并验证文件大小/哈希。因此仅修改客户端，发布工具仍需适配。
- 我方现有发布账户非管理员，只用于既有 OTA 目录发布，不能改全局设置。交接不包含账户口令、私钥或令牌。

## 当前发布状态

1.0.7 已打包、签名并完成三条 1.0.6 基线的真实升级测试；尚未上传发布，发布预检在远程写入前被 302 阻断。当前公开版本仍为 1.0.6。

1.0.6→1.0.7 只有前端 EXE、PDB 和版本文件，共 432,156 字节（约 422 KiB）；没有运行时或 Android 系统镜像。注意这只是最后一跳，旧版此前的运行时升级较大，不能将所有旧版升至 1.0.7 的总下载量也说成 422 KiB。

## 希望管理 AI 核查并回答

1. 当前 OpenList 版本、该分享对应的存储驱动，以及分享、Web 代理、下载代理、反向代理/CDN 的实际配置是什么？以匿名 HTTP 响应验证，不只看管理后台开关。
2. 是否可保留原入口，仅让小体积清单与签名直接返回 HTTP 200，而补丁对象仍用 302/307 等跳转到网盘/CDN？如何仅针对 OTA 目录配置，避免全局代理所有分享？
3. 若清单/签名独立静态托管，如何保持原 URL，并保证发布顺序、缓存更新与签名配对，避免读到新清单和旧签名？我方可以相应适配发布程序。
4. 旧更新器连补丁对象的跳转也不支持。只将清单改为 200 仍不能让它直接下载对象。请比较：
   - 针对 OTA 做有限、临时的兼容中转，让旧客户端获得支持直链的新更新器；迁移后大文件直连。
   - 用户运行一次很小的更新器修复工具，随后恢复正常 OTA。
   - 服务端是否存在其他能保持旧协议、同时避免文件中转的机制；如果不可能，请明确说明。
5. 临时兼容是否可按路径或迁移对象限定，而不依赖 User-Agent 作为安全权限判断？历史逐级补丁可能很大，请计算会中转哪些对象，不能只按最后一跳 422 KiB 估算。
6. 给出推荐拓扑、最小配置变更、必要客户端/发布端修改、迁移步骤、回滚方式和带宽影响。不要把未经核实的 OpenList 配置项当成已存在能力。

## 客户端与发布端的配合范围

我方可实现有界 HTTPS 跳转下载：限制跳转次数，拒绝降级 HTTP，不携带 OpenList 登录凭据到其他主机；下载完成仍必须验签、校验大小和 SHA256。不把短期签名直链写死到永久配置，不把账户密码发给最终用户。

更新器修复必须保留 Android 用户数据、应用和偏好。若修复会改动旧版本产品文件，还需与现有补丁的严格旧文件哈希检查协调；不能先任意覆盖再假设历史逐级补丁仍兼容。

“支持跳转”本身无法自动修复尚未取得新代码的旧客户端。这一引导迁移问题需要与直链长期方案一起设计。

## 验收标准

- 真实未修改的旧客户端能取得修复或有明确的一次性迁移操作；不能只用浏览器验证。
- 新客户端和发布端能匿名获取有效清单/签名，并下载、校验对象；不会收到登录页或错误 HTML。
- 旧版本逐级升级链保持有效，不降低签名和哈希校验。
- 用访问日志和传输字节数确认大对象下载实际直达网盘/CDN，OpenList 服务器只承担约定的小文件或临时兼容流量。
- 不改变无关分享的下载策略。

参考：[OpenList 全局配置：强制代理分享文件链接](https://doc.oplist.org/configuration/global#force-proxy-sharing-files)。该选项只是已知兼容手段，不是本次确定的长期推荐。
