# ArtemisOS 原生进程退出调查：3c49a730

日期：2026-11-11，时间均为 UTC+8。更新至 16:22，保留原始证据，以下结论按证据强度区分。

## 结论与责任

**已确认：本次是 Windows 模拟器 QEMU 原生进程崩溃，直接故障位于旧 SwiftShader GLES 图形库。** 不是仅凭 ARTEMIS 的设备离线提示判断；Windows Application Error、转储及实际模块路径相互印证。此次故障的直接修复责任在 ArtemisOS 集成的 Windows 图形运行时。

**高置信机制：检查帧缓冲对象状态时，读取渲染缓冲尺寸的虚函数调用进入纯虚函数终止处理，最终主动结束整个进程。** 这指向图形资源对象的状态或生命周期错误。尚不能在缺少对象堆内存与完整私有符号的情况下，断言具体是哪处释放后使用、哪一个并发线程或哪行源码错误。

## 从地址到调用机制

不能把“最近一个导出符号名 + 很大偏移”当作实际函数。本次继续读取 gfxstream 分派指针并反汇编，已超过原报告仅定位模块的阶段：

1. `libgfxstream_backend.dll` 基址 `0x00007ff9223b0000`。返回点 `0x00007ff9226b7fb9` 前设置 `ECX=0x8d40`，调用分派辅助函数。
2. 辅助函数跳转到 `qword[0x00007ff923930a50]`。转储中该指针实际指向 `0x00007ff92f4226e0`，导出为 **`glCheckFramebufferStatus`**；`0x8d40` 即 `GL_FRAMEBUFFER`。此处 API 识别来自真实分派指针。
3. 后续私有函数形态与 SwiftShader 的 `Framebuffer::completeness()` 及带 width/height/samples 参数的实现相符；返回点 `0x00007ff92f424833` 紧接一个获取尺寸的辅助函数。
4. 辅助函数读取对象的 `+0x18` 成员，再跳转到该对象虚函数表的 `+0x30` 槽；形态与 `Renderbuffer::getWidth() → mInstance->getWidth()` 相符。
5. 目标终止处理位于 `libGLESv2 + 0x151c30`，读取已注册处理器后进入终止流程。PE/RTTI 数据显示 `es2::RenderbufferInterface` 的纯虚槽，包括对应 getWidth 槽，使用同一处理入口。
6. 最终执行 `int 29h`，异常参数 `0=7`，为 **`FAST_FAIL_FATAL_APP_EXIT`**。不能仅把 `0xc0000409` 解释成栈溢出、内存耗尽或内存泄漏。

纯虚函数默认终止行为见 [Microsoft `_purecall` 文档](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/purecall)，fail-fast 参数语义见 [Microsoft `__fastfail`](https://learn.microsoft.com/en-us/cpp/intrinsics/fastfail)。具体对象失效原因仍是待验证推断，尚无释放栈。

参考源码为 AOSP `android10-release` 宿主 SwiftShader 历史实现： [Framebuffer.cpp](https://android.googlesource.com/platform/external/swiftshader/+/refs/heads/android10-release/src/OpenGL/libGLESv2/Framebuffer.cpp)、[Renderbuffer.cpp](https://android.googlesource.com/platform/external/swiftshader/+/refs/heads/android10-release/src/OpenGL/libGLESv2/Renderbuffer.cpp)、[Renderbuffer.h](https://android.googlesource.com/platform/external/swiftshader/+/refs/heads/android10-release/src/OpenGL/libGLESv2/Renderbuffer.h)。已保存这三个小文件并与二进制形态核对；没有证明它们就是该 DLL 的精确构建提交。该历史分支指宿主图形库参考，不代表客体系统是 Android 10；本机客体为 Android 15。

证据：`cdb-caller-details.txt`、`cdb-framebuffer-calls.txt`、`cdb-framebuffer-target.txt`、`rtti-and-dump-streams.json`。转储不包含相关对象堆页面，不能直接验证对象当前虚表、实际释放位置或完整资源生命周期。

## 软件后端的实际限制

**本机 37.3.6 Windows 包实测，`-gpu swangle` 仍回退到同一旧 SwiftShader GLES 库，不能作为本案的独立修复路线。**

15:56:44 使用同一 AVD 做临时 swangle 启动测试，QEMU PID 53908：请求参数确实为 swangle，但日志为 `gpu_mode_selected:swiftshader gles_mode_selected:swiftshader`，进程模块仍加载 `gles_swiftshader\libGLESv2.dll`，显示 SwiftShader 4.0.0.1。已停止该测试。

上游 [emugl_config.cpp](https://android.googlesource.com/platform/external/qemu/+/refs/heads/emu-master-dev/android/android-ui/modules/aemu-gl-init/src/android/opengl/emugl_config.cpp) 的 Windows 分支也明确将 swangle 转回旧 SwiftShader 路线。所查上游分支为 `emu-master-dev`，文件 blob `07c1a129a599927cc2aa0a7f674c0de835c4c5e5`，不是已确认的 37.3.6 精确源提交；本机二进制实测是主要证据。

[官方通用后端文档](https://developer.android.com/studio/run/emulator-acceleration) 列出模式名称，不足以保证每个平台都实现为独立后端。GUI 已去掉 SwANGLE 的独立备用方案暗示，明确提示本 Windows 版本回退。Lavapipe 未做本轮有效性验收，不能直接承诺它可替代故障 GLES 路径。

## 渲染与录屏是两条链路

- host 硬件渲染：Android 画面由 Windows 显卡图形驱动处理。本机实际使用 NVIDIA RTX 3080 Ti，驱动 621.14。
- SwiftShader 软件渲染：主要由 CPU 计算图形。模拟器的存在不代表一定采用软件渲染。
- 录像编码：把屏幕画面编码成 H.264 / HEVC。它与前面的图形渲染后端独立；使用 host 不代表 Android 录像已经获得 GPU 编码。

本机 `scrcpy 4.1 --list-encoders` 返回 H.264 `c2.android.avc.encoder`、别名 `OMX.google.h264.encoder`，HEVC `c2.android.hevc.encoder`，均标记软件编码。原事故录像实际为 HEVC、230 × 512、约 9.84 fps、时长 1002.575 秒。

ARTEMIS 的 auto 原先按 `hevc_playback` 判断浏览器能否播放 HEVC，未核查设备编码是否为软件实现。开发会话确认当前运行服务保存的其实是手动 h265。通用 auto 策略补丁要保留其他用户显式 H.265；本机排障另经用户在 ARTEMIS 开发会话明确选择“改为 H.264”，16:19 已通过 mobile_config 安全接口保存后续 H.264，回读确认只有 recording.codec 变化；不影响已有任务，也没有重启服务。该次用户授权的本机修改不能混为面向所有用户的强制迁移。

[Scrcpy 官方说明](https://github.com/Genymobile/scrcpy/blob/master/doc/video.md#codec) 默认 H.264，并指出其延迟通常较低。优先 H.264 是当前软件编码设备的合理降负载方向，具体 CPU 收益尚未做严格同场景基准；不能宣称已证明 HEVC 必然致崩。录制帧率上限不等于实际恒定帧率，静止画面会减少产生帧。

## 内存与历史问题的边界

转储 stream 22 revision 2、flags 0x0f 提供进程 VM 计数：PrivateUsage 7,270,608,896 字节（约 6.77 GiB），WorkingSet 4,261,273,600 字节（约 3.97 GiB），PeakWorkingSet 6,380,122,112 字节（约 5.94 GiB）。这是一份末端快照及峰值，不是长期增长曲线，不能证明内存泄漏。PageFaultCount 同时包括软缺页，不能直接据此判断磁盘交换或 OOM。JOB 标志未设置，其零值不能解释为已证明没有 Job 限制。

WinDbg 的 Analysis.Memory.CommitPeak 是分析器统计，不能用作 QEMU 内存峰值。14:30–15:10 本轮所取 Windows System 事件没有 2004/4101，不足以排除所有资源压力或驱动问题。
