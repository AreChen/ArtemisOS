# 直播卡死排查记录（2026-11-02）

## 问题与证据范围

用户确认移动爱家和联通智家均出现过类似问题。用户转述的另一份复盘提到：联通智家相关视频库曾在 `glAttachShader` 附近崩溃；另有一次 2560×1440 HEVC 解码平均延迟约 265 毫秒、最大约 556 毫秒，以及另一会话中 640×360 约 21 毫秒的记录。上述原始崩溃栈和性能日志目前不在本仓库，设备、进程和会话尚未逐项核实。两组耗时来自不同会话，不能视为严格对照。

调用栈涉及图形接口，提示应检查图形链路，但不能仅凭函数名认定是模拟器、显卡驱动或应用 SDK 中的哪一方出错。应用崩溃、Android 无响应、ADB 离线和 Windows 中 QEMU 被挂起也应分别判断。

## 本机检查和恢复

- 故障检查前，保存的配置为低配、图形自动、视频兼容开启；该次**实际启动**覆盖为 SwiftShader，并带 `-feature -HardwareDecoder`。图形软件渲染和视频解码兼容是两个独立开关。
- 本机旧的 QEMU 进程 286 个线程均显示 `Wait/Suspended`，三秒 CPU 增量为零，窗口不响应，ADB 为 offline。这说明检查时进程被挂起，不能单凭这些状态断言图形或解码崩溃，也没有证据确认挂起由谁触发。
- 恢复该进程后，窗口和 ADB 曾短暂恢复，随后进程退出；检查到的 Windows 应用事件和模拟器日志没有给出明确退出原因。
- 随后使用保存的自动图形配置重新启动，未清除 AVD 数据。Android 完成启动，移动爱家 99.0.0 仍已安装并可打开；短时采样中应用进程、模拟器窗口及 ADB 正常。此检查未覆盖直播长期播放或自动化任务，不能视为故障已修复。
- 该次自动配置实际选择了 NVIDIA 宿主硬件图形渲染，视频兼容仍开启。`auto` 在其他电脑上可能选择不同后端，不能从该机结果推断其他用户的实际设置。

## 本机视频解码线索

重启后的 Android `media.metrics` 中有一条 2304×1296 HEVC 软件解码记录，组件为 `c2.android.hevc.decoder`，平均延迟 124,511 微秒、最大 371,497 微秒、样本数 77；记录时间为 10:02:42。移动爱家进程于 10:02:24 启动，但目前没有直接证据把这条指标归属于该应用或某路直播。其平均值约为 125 毫秒，仅为该次解码器指标，不是屏幕端到端延迟或帧率。

[Android 15 MediaCodec 源码](https://android.googlesource.com/platform/frameworks/av/+/refs/heads/android15-release/media/libstagefright/MediaCodec.cpp)将这些延迟字段标为微秒。历史上的移动爱家摄像头解码对照详见[移动爱家 99 摄像头排查](移动爱家99-摄像头解码-20261031.md)：当时关闭 Emulator 的 `HardwareDecoder` 特性后，用户确认同一路画面恢复流畅；该结果不能自动推广到本次故障。

1. 在故障设备上，确认具体应用进程、ArtemisOS/Emulator 版本、实际 GPU 后端、视频兼容开关、虚拟 CPU/内存、显卡型号与驱动；记录应用无响应时 ADB、QEMU 和其他应用是否仍可操作。
2. 保留对应时间的脱敏 native 崩溃栈，包括异常类型、应用包名、`glAttachShader` 上下文及相关库；并记录同一会话的实际视频分辨率、解码组件和延迟。不要收集手机号、验证码、摄像头地址或访问凭据。
3. 在任务间隙或隔离实例中，固定视频源和测试负载，逐项对比硬件/软件图形、视频兼容开关和虚拟 CPU 配置，记录操作响应、应用崩溃、解码指标及宿主 CPU；不能把切换图形后端等同于切换视频解码。针对不兼容的显卡驱动，应保留可回退的软件图形选项。
4. 仅凭当前证据不修改面向所有用户的渲染或解码默认值，也不声称直播卡死已修复。
